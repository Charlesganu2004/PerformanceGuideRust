Details: why the setup without pgr is not counted

On the test machine, another tool altered some of the lines the agent without pgr read. In some runs it hid the very lines that show one of the callers the callers question asks for, so those agents left that caller out. That is a fact about the test machine, not about having no pgr.

Fully correct runs of the agent without pgr, original questions: 2 of 3 with Claude Haiku 5.5, low effort and 0 of 3 with Claude Sonnet 5.5, medium effort. Held-out questions: 3 of 3 with Claude Haiku 5.5, low effort and 2 of 2 with Claude Sonnet 5.5, medium effort. In the earlier session, which had no such tool: 4 of 5 with Claude Haiku 5.5, low effort, 3 of 3 with Claude Sonnet 5.5, medium effort and 3 of 3 with Claude Opus 5.5, maximum effort.

So pgr is set against the agent without pgr on tokens and turns only. Running that agent again with the other tool off, in the same session as the others, would remove the problem.

Search

Compared with neural search

The defaultInterval of the result

On 213 searches from commit messages, words alone had the right file in the first five results 93% of the time, both together 91%, and the small neural embedding alone 80%.

Words alone matched the default; the neural part alone was weaker than the default.

Adding the neural part did not improve on words alone.

A full neural network, in Rust, was tried three ways. In the first five results it had the right file 85% of the time alone, 94% of the time with words and 93% of the time with words and the small neural embedding.

Against the default: alone it was weaker; with words it was stronger; with words and the small neural embedding it was stronger.

Against words alone: alone it was weaker; with words it could not be told apart; with words and the small neural embedding it could not be told apart. None was stronger than words alone, so these searches do not show that the network adds anything to words.

The network did better than the default on searches by a function's own doc line (with words; with words and the small neural embedding). Those searches are a check on the method, because the text searched for is in the index, and are no evidence of a better search.

Beyond the interval of the result, it was worse than the default: alone, on test-name searches, commit searches and searches by a function's own doc line; with words, on test-name searches; with words and the small neural embedding, on test-name searches. The test-name searches are few, so read that as a direction.

Before the run we fixed a rule. A neural network could be recommended for the default only if it beat the default on the commit searches with the interval above zero, was not worse anywhere else beyond its interval, and cost little: the first build of the index of a small project in under 60 seconds, a search in under 200 milliseconds, and the program with its model file under 600 MB.

On one laptop, building the index of a small project, 86 files, took 25 minutes, against 0.5 seconds for the default; one search took 331 milliseconds, against 47; and the program with its model file is 336 MB, under the limit.

Under that rule none of the three could be recommended for the default.

Limits

  • The searches come from developer-written test names and commit subjects, not from questions an agent would ask.
  • In three of the code bases a single file is the answer to 40 to 53% of the commit searches, so credit piles up on that file.
  • Credit for a commit subject is lenient: any hit in a file the commit changed counts.
  • There are five code bases in three languages. One has no named tests, so it is judged on commit subjects alone.
  • The default was built by people who had seen none of these searches, and the figures here are the held-out half.
  • Every search weighs the same, so the larger code bases count more.
  • A test name and its answer share words by construction. The numbers compare ways of searching; they do not forecast how an agent will behave.
  • Credit goes to a block that contains the function, so a way of searching that returns bigger blocks gains from it. Stricter numbers are kept beside these in the data.
  • Answers in example, documentation, compatibility and legacy folders are left out. How pgr treats those folders is not measured here.
  • Other variations were tried on the other half of the searches. They are not shown on this page.
  • The full neural network was run three ways and all three are shown, on the held-out half only. None of them was tuned: the weights that combine the parts are those of the default.
  • What the full neural network costs was measured once, on one laptop that was in use at the time, so read the times as rough.

Read before relying on it

What this does not show.

  • The tests ran on one Python project of 86 files, with three lookup questions, on Claude Haiku 5.5, low effort and Claude Sonnet 5.5, medium effort.
  • The ready brief means pgr prepared the answers before the agent started. The agent had no command to call. The questions suit it: two of the three in each set name the function.
  • The people who built pgr wrote the questions. The second set was written after the first, but the ready brief was written after both had been run, so it is not an untouched test.
What was asked
  • Who calls a function. Name every function in the repository that calls a given function.
  • Where a function is defined. Give the file and the line where a named function is defined, its parameter names and the functions that call it.
  • Which function does a job. Given a described job, name the function that does it, say where it is defined and name its counterpart, the function that reverses it.

One agent answered all three questions in a run. A second set of three questions of the same three kinds, written later by the same team. The people and agents who built pgr through the first five tests did not see them while building. The ready brief was written after these questions had been run, so for the brief they are a second set of questions, not an untouched one.

The held-out questions were run on 14 setups, with 2 to 3 runs in each test. They are not independent: the same team wrote both sets, on the same project, in the same three shapes. They check whether pgr was fitted to the first three questions, not whether it works on other kinds of question.

Who answered
  • Claude Haiku 5.5, run at low reasoning effort. The smallest of the three.
  • Claude Sonnet 5.5, run at medium reasoning effort. The middle one.
  • Claude Opus 5.5, run at maximum reasoning effort. The largest.

The runs were made from 7 October 2026 to 14 October 2026. The runs asked for a class of model by alias; these are the models those aliases meant on the days of the runs.

How answers were graded

Every answer was checked by a script against an answer key, and no score was given by a person judging an answer. The keys for the callers and definition questions were read from the project itself; the key for the which-function question was written by hand. The authors reviewed all of them. For the which-function question on the held-out set, the key accepts either of two functions, because both do the job.

Each answer scores between 0 and 1, with partial credit: a list of callers scores by how many are named and how many are wrong. A run is fully correct when all three of its answers score full marks, so one missed caller is enough to make a run not fully correct.

How tokens were counted

The tokens of a run are the input, the output and the cache reads and writes of the agent, added up over the whole task. 99% of the tokens counted in the 172 runs behind the table were cache reads or writes.

An agent starts with a context of about 65.9k tokens: the instructions, skills and tool descriptions of the test machine. Every turn reads it again, so tokens and turns are one measurement counted twice.

How many runs

172 runs in 62 tests stand behind the table: 5 tests of 1 run; 4 tests of 2 runs; 53 tests of 3 runs. In all, 1,235 agents and 634 runs were made, which also count setups that are not published and tests of other tools; they show effort, not the sample behind a result.

59 setups were tested and 22 are published here. The authors chose which to publish; no rule did.

Dates and sessions

Two sessions. The setups marked Earlier session were measured in the first session and not repeated, and their tokens are not directly comparable with the rest: the start-up context grew by 3% between the sessions, and every turn reads it again. 10 of the 25 setups that were tested and not published, run at least 3 times on the smallest model and the original questions, also took 2 turns with every run fully correct.

The search comparison was measured on 14 October 2026, and the rows of the full neural network on 20 October 2026.

All the limits
One project
Every result comes from one Python project of 86 files. Other projects may behave differently.
One language
The agent tests used Python only. The search comparison used code in more than one language, but no agent ran on it, so nothing here says how an agent does on other languages.
Six questions
Six lookup questions of modest difficulty, in two sets of three. Only one question separates the setups: of the 26 runs that were not fully correct, 20 missed part of the answer to "Who calls a function". The "Which function does a job" question was fully answered in 166 of 172 runs, 23 of 23 of them by setups without search, so these runs cannot show whether searching by meaning helps. Harder questions may separate the setups more, or less.
Questions that suit the tool
Two of the three questions in each set ask for the callers of a function, which pgr answers directly, and none was written to need the body of a function to be read. Questions about what a function does may come out differently.
A weak baseline
The agent without pgr had only its own basic file search and file reading. A stronger unaided agent, with a shell and a search that understands code, was not measured, so the savings are against this baseline only.
Few runs, one task
Each test holds 1 to 3 runs, and every run answers the same 3 questions, so the runs of a test are repeats of one task, not samples of many. Three runs cannot support a claim of significance, and this site makes none. A difference of one run or one turn is inside the run-to-run spread. In the 57 tests with at least two runs, the highest run used 26% more tokens than the lowest at the median and 215% more at most, and in 23 of them at least half as many again. One turn is about 69k tokens. In 11 tests some runs were fully correct and some were not.
Unequal instructions
Each agent was given a description of its own tool. The descriptions differ in length and detail, and this was not controlled.
The same team
The same team built pgr, wrote both question sets and ran the tests.
Start-up context
An agent starts with about 65.9k tokens of context from the test machine: its instructions, skills and tool descriptions. On another machine each turn costs a different number of tokens, and so does the saving.
Machine load
Wall time depends on what else the test machine was doing. Token counts do not.
Money
A token read from the cache costs less than one that is not, so a saving in tokens is not a saving in money of the same size. This site gives no money figures.

Open-ended work was not tested. How pgr does for teams of agents, and how far each part was measured, is on the Teams page.
